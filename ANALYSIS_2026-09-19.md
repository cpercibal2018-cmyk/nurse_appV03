## 3. Findings, ranked

### F1 — The backend cannot serve the API its own README documents *(blocker)*

`backend/src/modules/roles/roles.controller.ts:24`:

```ts
// Mock JwtAuthGuard for demo — …
class JwtAuthGuard { canActivate() { return true; } }
```

Nothing in the codebase ever sets `req.user`. Therefore:

* `RolesGuard.canActivate` (`common/guards/roles.guard.ts:20`) reads `request.user`,
  gets `undefined`, and throws `ForbiddenException('Not authenticated')` on every
  `@RequireRole` route.
* The routes that would get past the guard (`/me`, `assignments` CRUD, approvals, PAM)
  immediately dereference `req.user.id` → `TypeError` → HTTP 500.

There is no auth module, no `passport`/JWT dependency in `backend/package.json`, no
cookie parser, and no CSRF guard in `backend/` — the CSRF ordering work (B-04) exists
only as `wave1a-kit/backend/tests/csrf-guard-order.e2e-spec.ts`. `backend/README.md`
nonetheless documents a full API table with status codes.

### F2 — `backend/` has no `tsconfig.json` (verified failure)

`npm run build` → `TS5058`. Also missing: `backend/prisma/seed.ts` (referenced by
`npm run seed`) and `backend/prisma/migrations/`.

### F3 — The constraints the code relies on exist only as comments

`prisma/schema.prisma`:

```
// Partial unique enforced via raw SQL migration: only one active per user+role+scopeType
// Partial unique WHERE status=PENDING enforced via raw SQL
// Contract.jobNumber … exclusion constraint GiST daterange && WHERE status IN (Approved,Active)
```

No migration directory exists in `backend/`. So `uq_user_role_active`,
`uq_admin_request_pending` and the contract-overlap exclusion are never created;
`grant()`'s `catch (P2002)` can never fire from them, and the duplicate check is an
in-transaction `findFirst` — race-prone without the index it claims to be backed by.

### F4 — Idempotency in `backend/` contradicts both its README and `wave1a-kit`

* `IdempotencyKey` has only `expiresAt` (24 h). There is **no** `processingLeaseExpiresAt`,
  so B-08's "409 only while the lease is live; lapsed keys retaken" is not implemented —
  a retry returns **409 for 24 hours**.
* `checkIdempotency()` writes the key row in its own statement, not in the business
  transaction, contradicting the README's "key row committed with business mutation same
  transaction".
* On the four-eyes path `grant()` creates the key and then `throw new HttpException(…, 202)`.
  The key is orphaned with a live 24 h TTL, so a client retrying the same `Idempotency-Key`
  gets 409 instead of the pending request it just received.
* `wave1a-kit/backend/src/common/idempotency/` implements the lease version correctly and
  the kit's verifier checks it. Two incompatible implementations of B-08 ship in one repo.

### F5 — `expireDue()` will fail at the database *(unverified — no DB here)*

`roles.service.ts:326` audits with `actorId: 'system'`, while
`AuditEntry.actorId` is `String @db.Uuid`. Postgres rejects that with SQLSTATE 22P02
(`invalid input syntax for type uuid`), so the role-expiry worker throws on the first
expired assignment. Use a reserved system-principal UUID or make the column nullable.

### F6 — The audit hash chain is not serialised

`AuditService.log` / `logTx` do `findFirst({ orderBy: { createdAt: 'desc' } })` then
`create` — no advisory lock, no unique constraint on `prev_hash`, no DB-side
`fn_append_audit_entry`. Two concurrent transactions can read the same tail and fork the
chain, and `createdAt` is not a reliable tie-breaker. §9.1 (quoted verbatim in
`app/README.md`: "audit_entries DDL + fn_append_audit_entry (hash, previous_hash, advisory
serialized)") requires the DB function; `gate1-kit/sql/10_audit_chain.sql` contains exactly
that implementation, and `backend/` does not use it.

### F7 — Scope enforcement is set membership on raw IDs

`assertScopeCoverage` carries its own admission — *"Real implementation would join
departments/units and check inclusion"*. Effects:

* A DEPARTMENT-scoped HR_ADMIN gets a false 403 when granting UNIT roles inside their own
  department (a department id never equals a unit id).
* No cross-type check between the actor's scope type and the requested scope type.
* `list()` has the same hole, also self-documented: *"Real implementation would filter by
  actor's scopeIds"* — a scoped HR_ADMIN reads system-wide assignments.

### F8 — Five routes are declared with `..` path segments

```ts
@Controller('api/v1/roles')
  @Get('/../admin/approvals')   …also :requestId/approve, /reject, /../admin/pam/elevate, /status
```

In an express 4.22.1 harness (the version Nest 10 installs; its bundled matcher is
path-to-regexp 0.1.13) the pattern compiles to `/^\/\.\.\/admin\/approvals\/?$/i` and
matched only a request sent with the **un-normalised** target
`GET /api/v1/roles/../admin/approvals` (200). HTTP clients normalise `..` before sending,
so the documented `GET /api/v1/admin/approvals` does not reach it. *The Nest-level route
table was not executed here — see Blocked.* Fix: a separate `@Controller('api/v1/admin')`.

### F9 — `RolesGuard` over-blocks on PAM

The PAM check fires whenever the actor *holds* any `SYSTEM_ADMIN` assignment, irrespective
of which role the route required. A user with both SUPERVISOR and SYSTEM_ADMIN assignments
is 403'd on SUPERVISOR-only endpoints until elevated. The check belongs to the SYSTEM_ADMIN
authorisation path, not to the role-membership path.

### F10 — The frontend never calls the backend

`grep -rnE "fetch\(|axios|XMLHttpRequest|import.meta.env" app/src` returns **zero** call
sites — every `/api/v1/…` string in the app is display text inside an Ant Design
`Alert`/`Descriptions.Item`. Data comes from `src/data/seed.ts` + Zustand + `localStorage`
(`app/src/lib/api/roles.api.ts`, storage keys `aigh_pending_approvals`, `aigh_audit_log`).

`roles.api.ts` also re-implements the backend's rules in the browser (reason ≥ 20 chars,
self-grant block, last-SYSTEM_ADMIN block, 202 four-eyes, "partial unique index" duplicate
message). §8 is explicit that the browser must never be the authority — acceptable for a
demo, misleading if read as a client.

### F11 — CI is a fragment that cannot run

`wave1a-kit/ci/ci.yml` invokes `npm run build:backend`, `test:unit`, `test:pg`, `test:http`,
`build:frontend`, `npx jest --config test/jest-wave1a.config.ts`,
`node scripts/check-bundle-size.mjs` and `npm run lint`. **None** of those npm scripts exist
in either `package.json`; the jest config does not exist; `check-bundle-size.mjs` lives at
`app/scripts/` and `wave1a-kit/scripts/`, not repo root; `npm run lint` fails with exit 127;
and there is no `.github/` directory at all. B-02's "CI green on Node 20 / PG 15" has no
evidence in-repo.

### F12 — No container or proxy artefacts

No `Dockerfile`, `docker-compose*`, or `nginx.conf` anywhere in the tree, although review
findings F-21/F-22 and tracker items B-20/B-21/B-22 depend on them.

### F13 — The i18n claim is overstated (the underlying work is good)

`app/src/lib/i18n.tsx` has **46 keys with verified 100 % en/ar parity** (0 missing in
either direction) and correct `dir=rtl` switching on `document.documentElement` and
`document.body`. But `useTranslation` appears in only **3 of 18** components
(`AppLayout`, `LoginPage`, `DashboardPage`; 22 `t()` calls). The other 16 pages are
hardcoded English — `AdminModule.tsx` alone has 40 `title=/label=/message=/description=`
props. `app/README.md` §2.10's "no hardcoded strings" is false.

### F14 — Documentation drift

* Root `README.md`'s path table lists 13 entries and **omits `app/` and `backend/`** — the
  two largest code artefacts in the repo.
* `ANALYSIS.md` still opens by describing a repository of two files. It is now 118.
* `ANALYSIS.md` Finding 2 says the GPG key "remains in commit `09828e0` until history is
  rewritten". **That commit does not exist here** — `git cat-file -e 09828e0^{commit}` →
  `fatal: Not a valid object name`; `git rev-list --all --count` → **1**; scanning all 182
  objects for `PRIVATE KEY BLOCK` / `BEGIN RSA PRIVATE` returns **nothing**. The exposure is
  closed. The note is stale and should be updated (the *practice* warning is still worth
  keeping).
* `ANALYSIS.md` says "101 patches" in its inventory table and 102 in its own fix note.
  Actual: 102.
* `ANALYSIS.md` claims "120 / 245 / 47 / 582 match across backup.log, postgres.log and both
  evidence files". **The row counts appear only in the two evidence `.md` files** — neither
  log contains any count. What the logs *do* corroborate is the timeline and the PITR
  mechanics (see §4).
* Bundle figures are stale but the gate still passes: docs say 3,097 modules / entry
  64.6 KB gz / `RoleMatrixPage` 11.90 KB gz; measured today 3,098 / **65.71 KB** / 11.89 KB.
* Both `gate1-drill/*evidence.md` files still have **empty Operator and Reviewer sign-off

## 4. What the gate1 drill evidence does and does not prove

Corroborated by the committed logs:

* `backup.log`: 7 WAL segments `…0001`–`…0007` archived; base backup
  `basebackup_20260918_110341.tar.gz.gpg`, 3,956,103 B, sha256 `ee705c96c40b…`;
  restore started 11:03:45, "recovery complete — database promoted" 11:03:48 → the
  evidence file's "Elapsed (restore) 3 s" checks out.
* `postgres.log`: PostgreSQL **15.19**; genuine crash/PITR recovery —
  *"database system was not properly shut down; automatic recovery in progress"*,
  `redo starts at 0/2000028`, `redo done at 0/50140D8`.
* `archive_timeout=300` is independently corroborated: checkpoint completed 11:03:49.000,
  next time-based checkpoint started 11:08:49.100 — 300.1 s later. The evidence's
  298 s commit→archive figure is consistent with that bound within log granularity
  (11:03:50.208 → the 11:08:49 archive line is 298.8 s), and ≤ 300 s either way.

Not provable from the repo:

* The row counts (120 employees / 245 audit rows / 47 units / 582 beds / 480 credentials)
  exist only in the markdown. The encrypted backup and WAL segments are deliberately
  gitignored, so the PASS rows cannot be re-derived — by design, but it means the evidence
  is attestation, not reproduction.
* Sign-off is unsigned.

## 5. Genuinely strong parts

1. **The spec generator is reproducible.** A 423,742-byte document rebuilt byte-for-byte
   from a pristine source by 102 declarative patches, with an SHA-256 assertion and a
   32-finding integration verifier. That is rare and worth protecting.
2. **`wave1a-kit` is the best code in the repo.** It implements what `backend/` only
   describes — lease-based idempotency, worker leases with conditional upsert and
   per-process identity, fail-closed KSA residency check, dry-run-by-default CSV import,
   guard ordering — and ships a verifier that actually executes (44/44).
3. **Frontend code-splitting is real and measured**, not aspirational: 14 lazy routes,
   vendor split, `NavLink` preload, `PageSkeleton` fallback, and a budget gate that runs
   and passes.
4. **Domain data is consistent across three independent places** — `seed.ts`, the gate1
   evidence files, and tracker B-01 all agree on 47 units / 582 beds with a matching
   per-department breakdown.
5. **Secret hygiene at HEAD is correct**: `.gitignore` covers keyrings, `*.key`, `*.gpg`,
   `gate1-drill/backup/`, and the scan of all git objects finds no private key material.
