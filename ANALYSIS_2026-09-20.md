## 3. Findings, ranked

### N1 — `npm test` crashes on an eagerly-evaluated fetch *(blocker, regression)*

`app/src/lib/api.ts`:

```ts
const BASE = (import.meta as any).env?.VITE_API_URL as string | undefined;
export const API_ENABLED = !!BASE;

async function req(path: string, init?: RequestInit) {
  const res = await fetch(`${BASE}${path}`, { … });   // ← BASE is undefined here
}

export function syncWrite(p: Promise<any>) {
  if (!API_ENABLED) return;                            // ← guard runs too late
  p.catch((e) => console.warn('[api] write failed (kept local):', e.message));
}
```

Call sites are `syncWrite(api.create('employees', newEmployee))` — `store.tsx:587, 588,
596, 601, 694, 911, 916`. JavaScript evaluates the argument **before** the call, so
`req()` has already run `fetch("undefined/api/employees")` by the time `syncWrite` decides
to do nothing. Because it returns early it also never attaches `.catch`, so the rejection
is **unhandled**.

* **In Node** (the test harness bundles the real `store.tsx` with esbuild): unhandled
  rejection ⇒ Node 22 terminates the process. That is the exit-1 crash at section `[9]`.
  The second half of `npm test` — the bundle gate — never runs at all.
* **In a browser** in standalone mode (`VITE_API_URL` unset, the mode `RUN_LOCALLY.md`
  recommends for a quick look): `"undefined/api/employees"` is a *relative* URL, so every
  write issues a real `POST /undefined/api/employees` against the dev server. Verified:
  that path returns **404** ⇒ `req()` throws ⇒ unhandled rejection in the console. The
  demo silently generates bogus traffic and console errors on every save.

**Fix (one line, proven):** guard inside `req`, which covers all seven call sites at once.

```ts
async function req(path: string, init?: RequestInit) {
  if (!API_ENABLED) return null;   // standalone: no backend configured, nothing to sync
  const res = await fetch(`${BASE}${path}`, { … });
```

I applied exactly this, re-ran the suite, then reverted it (the tree is clean). It stops
the crash — and reveals N2. **It does not make `npm test` green.**

### N3 — The v2 migration silently destroys user contracts *(high, data loss)*

`store.tsx:1040`:

```ts
migrate: (persistedState, version) => {
  const migrated = { ...persisted, employees: normalizePersistedEmployees(persisted.employees) };
  if (version < 2) {
    migrated.contracts = CONTRACTS_SEED as Contract[];   // ← wholesale replace
  }
  return migrated;
}
```

`partialize` persists `contracts`, so any browser session saved at v1 that contains
**real, user-created contracts** has all of them thrown away and replaced with eight demo
rows on the next load. The v1 step (`normalizePersistedEmployees`) is correct — it maps
each row and strips a retired prefix. The v2 step should do the same: normalise *statuses*
on the persisted rows, or merge, not overwrite. Tolerable in a demo, but this is the
pattern that loses clinical contract history in production, and it is the migration the
HEAD commit just added.

### N4 — The runnable API has no authentication or authorisation at all *(blocker, security)*

`server/src/index.ts` is 91 lines. Its entire middleware stack is `cors()` +
`express.json()`, followed by a generic CRUD router over 12 entities. `/api/auth/login`
mints a `'demo-' + Math.random()` token that **no middleware ever reads**.

Consequences, all reachable by any client that can reach port 3001:

* `GET /api/bootstrap` returns every row of every table. `Employee` includes `salary`,
  `nationality`, `maritalStatus`, `contactEmail`, `fileNo`, `rankGrade`. This is exactly
  the PDPL-scoped PII that §8.3 protects and §8.1 says must be filtered by record scope
  and *permitted response fields*. There is no scope filtering of any kind.
* **`audit-entries` is a registered entity**, so `POST`, `PUT` and `DELETE
  /api/audit-entries/:id` are open. The specification's central integrity control —
  append-only, hash-chained audit (§9.1, `fn_append_audit_entry`) — is directly
  defeatable: anyone can rewrite `hash`/`previousHash` or delete rows and leave no trace.
  `ROLE_MATRIX.md` §2 says Employees get "Own history only" and Supervisors "No audit by
  default"; the API gives everyone write access.
* No CSRF protection, no rate limiting, no `helmet`, no input validation — `req.body` is
  passed straight to `prisma.…create({ data: req.body })`, so a client controls every
  column including `id`, `hash` and `isActive`.
* `cors({ origin: process.env.CORS_ORIGIN || true, credentials: true })` — if `CORS_ORIGIN`
  is unset this reflects **any** origin while allowing credentials.

The repository now contains three backends with three different security postures:
`ROLE_MATRIX.md` documents a 4-role least-privilege matrix, `backend/` implements guards
(broken — see F1), `wave1a-kit/` implements guard ordering correctly, and **`server/` —
the only one that actually runs — implements none of it.**

### N6 — The full stack bakes `http://localhost:3001` into the browser bundle *(high)*

`docker-compose.yml` passes `VITE_API_URL: http://localhost:3001` as a **build arg**;
`app/.env.example` recommends the same. Vite inlines that string at build time and the
*browser* then calls it directly (`api.ts` has no proxy path). So the stack only works
when the browser is on the Docker host. Accessed by LAN IP, through a tunnel, from a
phone, or from the Arena preview host, the SPA calls the *viewer's own* localhost — and an
HTTPS page calling `http://localhost` is blocked outright as mixed content.
`CORS_ORIGIN=http://localhost:5173` is the mirror-image problem.

`vite.config.js` defines no `server.proxy`, so there is no fallback. The fix is the
standard one: use relative `/api` URLs and proxy — Vite `server.proxy` in dev, nginx in
production (the `proxy:` service `docker-compose.full-spec.yml` already intends).

### N8 — The boot-blocking residency check runs in the browser *(medium)*

`app/src/main.tsx` `assertResidencyFromEnv()` compares a build-time `VITE_AWS_REGION`

### N9 — Only three of twelve entities are written through; `RUN_LOCALLY.md` overstates it *(medium)*

`syncWrite` appears at seven call sites covering **`employees`, `contracts` and
`shift-assignments` only**. `RUN_LOCALLY.md` states: *"Creating/editing employees,

### N10 — The server schema types away every constraint the spec depends on *(medium)*

In `server/prisma/schema.prisma` (12 models) **every date and time is `String`**:
`hireDate`, `contractStart`, `contractEnd`, `startDate`, `endDate`, `shiftDate`,
`startTime`, `createdAt`, `verifiedAt`, `lastSyncAttempt`.

* No `daterange`/GiST exclusion constraint is expressible. `app/src/lib/contracts.ts`
  documents its overlap rule as *"the exclusion constraint `GiST daterange && WHERE status
  IN (Approved, Active)` which rejects overlapping coverage periods"* — against this
  schema that rule exists **only in the browser**, which §8 forbids.
* No temporal indexing, no timezone semantics; ordering and range comparisons are
  lexicographic string operations.
* **Nine of the twelve models have a primary key with no `@default(autoincrement())`** —
  seven declare `id Int @id`, two declare `code String @id`; only `ShiftAssignment`,
  `Notification` and `AuditEntry` auto-increment. So any `POST /api/:entity` that does not
  supply an explicit key fails at the database.
* `Contract`, `Credential` and `CredentialRequirement` declare **no relations**, so there
  are no foreign keys — orphaned contracts and credentials are possible, and the
  hand-ordered `deleteMany` chain in `seed.ts` is the only thing keeping the tables tidy.

`backend/prisma/schema.prisma` (34 models) types all of this properly. The runnable schema
is the weaker one.

### N11 — The audit hash chain in the store is not the specification's *(medium)*

`store.tsx:278` `simpleHash()` is a 32-bit djb2 variant concatenated with
`Date.now().toString(16)`:

* Not SHA-256 (§9.1 requires a SHA-256 chain).
* It embeds wall-clock time, so **the same entry hashes differently on every replay** — no
  verifier can recompute the chain, which defeats the purpose of a hash chain.
* `previousHash` is taken from array position (`s.auditEntries[length-1]`), not from an
  ordered tail, and `id` is `auditEntries.length + 1`, which collides after any deletion
  or after `hydrateFromApi` loads DB-assigned ids.
* `gate1-kit/sql/10_audit_chain.sql` contains the correct SHA-256 + advisory-locked
  `fn_append_audit_entry`. Nothing executes it.
