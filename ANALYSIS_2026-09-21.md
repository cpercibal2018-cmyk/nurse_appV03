> ### Update — item 5 executed: WAL is now bounded, and kit runs are exclusive
>
> `nightly-backup.sh` gained three things, `restore-database.sh` two.
>
> **Base-backup-aware WAL retention (G3).** Step 4a records the backup's own WAL start
> segment in the sidecar — parsed out of `backup_label` inside `base.tar.gz` *while the
> plaintext still exists*, because after step 5 the only copy is a `.gpg` and this host
> holds no private key (F-23 FIX 3), so that is the last moment the value can ever be read.
> Step 7 then removes archived segments strictly **before** the oldest *retained* backup's
> segment and keeps everything from it forward. The floor is deliberately neither a date nor
> an mtime: a WAL file's mtime is when it was *archived*, which is after it was written, so
> an mtime sweep keyed on a backup's own mtime deletes segments that backup still needs.
>
> **Retention floor guard (G6).** Base-backup pruning no longer runs
> `find … -mtime +N -delete` over the archive *and* its sidecar, which could delete the last
> restorable backup whenever every file was past the threshold — a misconfigured
> `BACKUP_RETENTION_DAYS=0`, or clock skew on the storage volume. The newest backup is never
> pruned, and a sidecar is removed only together with the archive it describes, since an
> archive without its sidecar cannot be verified on restore (G2). Retention runs *before* WAL
> pruning precisely because the floor means "the oldest backup that survived retention".
>
> **Mutual exclusion (G6).** Both scripts take one shared `flock` (`GATE1_LOCK_FILE`, default
> `${BACKUP_STORAGE_PATH}/.gate1.lock`) and are **refused** rather than queued. The real
> conflict is not I/O: it is a backup applying retention and pruning `wal/` underneath a
> restore that has already chosen a base backup and is minutes into replaying WAL.
> `wal-archive.sh` and `wal-restore.sh` deliberately never take it — PostgreSQL spawns them
> through `archive_command` / `restore_command` *while* the lock is held, so locking there
> would deadlock the very recovery the holder is waiting for. A missing `flock(1)` fails
> **open** with a warning: "no backup exists" is a worse DR outcome than "backup taken
> without mutual exclusion".
>
> **Same-second collision (G6).** The lock serialises runs but does not make the timestamp
> unique — a run that finishes inside the same UTC second computes the same `BACKUP_FILE`
> and would silently overwrite a backup already in the archive. It now refuses instead.
>
> **Word-splitting (G6).** `restore-database.sh`'s `for f in $(ls -1 … | sort)` became a
> `nullglob` array, so a storage path containing spaces no longer turns one backup into
> several bogus candidates.
>

> `flock`: **25 scenarios / 113 assertions**, all passing — with a stub `pg_basebackup` that

## 1. Method — including one near-miss worth recording

**The API harness.** `server/src/index.ts` imports `@prisma/client`, whose generated client
cannot exist here (`binaries.prisma.sh` is unreachable; the npm registry is not). So I
bundled the **real, unedited** source with esbuild, aliasing only that one import to an
in-memory stub exposing the same delegate surface (`findMany`/`create`/`update`/`delete`/
`deleteMany`/`count` per model, plus `$queryRaw`). The stub was seeded with representative
rows including a three-link audit chain. The bundled server was booted on port 3999 and
probed with plain `curl` — **no cookies, no `Authorization` header, no CSRF token** unless
a probe says otherwise. Everything in §2 is a real HTTP response from the project's own
route handlers.

**⚠️ A false finding I nearly published.** My first Prisma stub declared the enums as
TypeScript `enum`s. `tsc` then reported **12 errors** in `backend/src` — `TS2352` on
`string → AppRole` casts and `TS2367` on `AppRole === string` comparisons in
`roles.guard.ts` and `roles.service.ts`. That looked like a substantial new finding.

It was an artifact. Prisma 5 codegen does **not** emit TS enums; it emits a `const` object
plus a string-literal union of the same name:

```ts
export const AppRole = { SYSTEM_ADMIN: 'SYSTEM_ADMIN', … } as const;
export type  AppRole = (typeof AppRole)[keyof typeof AppRole];
```

With the stub corrected to that shape, `backend/src` compiles **clean**. The 12 errors were
mine, not the project's. Recorded here because Part I's F1–F9 were all "by inspection", and
this is exactly how an inspection-based review manufactures a defect that isn't there.

### The audit chain, before and after three anonymous requests

```
BEFORE                                    AFTER
 id 1 EMPLOYEE_ONBOARDED    hash a1b2c3    id 1 NOTHING_HAPPENED  hash forged00   prev null
 id 2 CONTRACT_APPROVED     hash d4e5f6    id 2 CONTRACT_APPROVED hash d4e5f6     prev a1b2c3  ← dangling
```

The break-glass elevation record is gone, a hash is forged, a fabricated entry is
backdated to 2020, and `id 2`'s `previousHash` now points at a value that no longer
exists. **§9.1's append-only, tamper-evident guarantee is not merely unimplemented here —
it is inverted into an anonymous write/delete endpoint**, and the severed link is exactly
the kind of damage a hash chain is supposed to make detectable.

### Probe 12 is a distinct bug worth its own line

```ts
const cfg = ENTITIES[req.params.entity];
if (!cfg) return res.status(404).json({ error: 'Unknown entity' });
```

`ENTITIES` is an object literal, so the lookup walks the prototype chain. `constructor`,
`__proto__`, `toString` and `hasOwnProperty` are all truthy, the 404 guard never fires,
`cfg.model` is `undefined`, and the resulting `TypeError` is serialised straight to the
client — leaking internal structure. Fix: `Object.hasOwn(ENTITIES, req.params.entity)`, or
a `Map`; and stop returning `e.message` to callers (`catch (e) { res.status(500).json({
error: e.message }) }` appears on the bootstrap route too).

## 5. The Gate 1 DR kit, reviewed properly (new ground)

Previous analyses ran `bash -n` and stopped. **Credit first, because it is earned:** all
ten scripts set `set -euo pipefail` and quote their variables carefully, including in every
destructive path. `wal-archive.sh` is genuinely excellent — encrypt to `$$`-suffixed temp,
verify the envelope is a real public-key message, atomic `mv` into place, `trap` cleanup —
and it correctly diagnoses and handles a subtle trap: `gpg --list-packets` exits non-zero
when the private key is absent (the normal case on a backup host), which under `pipefail`
would fail a *valid* archive, so the output is captured and the status deliberately
ignored. `restore-database.sh` carries comments recording three real failures found and
fixed during the drill (`-U postgres` being required or the `|| echo 't'` fallback masks a
connection error and burns the whole timeout; `archive_mode=off` so a promoted drill target
cannot write into the archive it is recovering from; stopping a leftover postmaster
*before* `rm -rf` of its data directory). The F-23 corrections are right for PG 15.

Then the defects.

### G1 — Decrypted plaintext of the entire database is left on disk after every restore *(PDPL, high)*

`restore-database.sh:60-67` decrypts the base backup into `${RESTORE_PARENT}/unpack` and
extracts `base.tar.gz` + `pg_wal.tar.gz` there. `UNPACK_DIR` is `rm -rf`'d only at the
**start** of the next run (line 61); there is no cleanup at the end and no `trap`. After a
successful restore and promotion the script exits, leaving an **unencrypted copy of the
whole production database — all employee PII — on the restore host indefinitely**.

Same class of problem upstream in `nightly-backup.sh`: `pg_basebackup` writes a plaintext
`base.tar.gz`, `tar -czf` makes a *second* plaintext copy, and only then is it encrypted
and `rm -rf`'d (line 79). `rm` does not zero blocks, so a gzipped-but-recoverable copy of
the database persists in freed space on the backup volume after every run — which is
precisely what §8.3's encryption-at-rest posture exists to prevent.

*Fix:* `trap 'rm -rf "${UNPACK_DIR}"' EXIT` in the restore; and stream the backup
(`pg_basebackup -Ft -z … | gpg --encrypt`) or stage on `tmpfs` so plaintext never reaches
persistent storage.

> **🟠 PARTIALLY CLOSED (item 4, executed).** The **restore half is fixed**: `UNPACK_DIR` is
> now declared above every exit path and removed by `trap … EXIT`, so no run — success,
> failure or signal — leaves decrypted plaintext behind. Proved by stubbing `gpg`, `pg_ctl`
> and `psql` (none exist here) and driving the *real* script all the way to a successful
> promotion: exit 0, `recovery complete — database promoted`, `unpack/` gone, restored
> `PG_VERSION` present. Also proved on a late failure (decrypt yields junk → non-zero exit
> with `unpack/` still removed) and on every early-exit path below.
>
> The **upstream half remains open** and is item 8: `nightly-backup.sh` still writes a
> plaintext `base.tar.gz` plus a second plaintext copy via `tar -czf` to the backup volume
> before encrypting, and `rm` does not zero blocks. Streaming the encryption or staging on
> `tmpfs` is the fix. It needs a live PostgreSQL to verify honestly, so it was not attempted.

### G2 — The SHA-256 that the backup job records is never verified on the restore path *(high)*

`nightly-backup.sh` computes `CHECKSUM` and writes `"checksum_sha256"` into
`basebackup_*.meta.json` — for exactly this purpose. **Nothing ever reads it back.** The
only references to `.meta.json` in the whole kit are the `cat >` that writes it and the
retention `find` that matches it by filename; no script runs `sha256sum -c`, and grep
across the five restore-side scripts (`restore-database.sh`, `restore-drill.sh`,
`pitr-proof.sh`, `failure-drill.sh`, `wal-restore.sh`) returns **zero** hits for `sha256`,
`checksum` or `meta.json`.

The ordering makes it worse: `rm -rf "${RESTORE_DIR}"` (line 58) destroys the previous
restore tree **before** `gpg --decrypt | tar -xzf` (line 64) is attempted. A truncated or
corrupted object in storage therefore surfaces as a mid-restore pipe failure, after the
prior good state has already been deleted.

This also undercuts the spec's V43 `backup_verification_age` metric, which presumes
verification happens on a schedule. Nothing here performs a periodic restore-verify, so a
bad backup is discovered only when a human runs a drill.

> **✅ CLOSED on both ends (item 4, executed).**
>
> *Restore path:* `restore-database.sh` reads `checksum_sha256` **and** `size_bytes` from
> `basebackup_*.meta.json` and verifies the object **before** the destructive
> `rm -rf "${RESTORE_DIR}"` (verification block at lines 83–121, deletion at 133 — asserted,
> not assumed). Parsed with `sed`, not `jq`: a host in the middle of a recovery is the worst
> possible place to discover a missing dependency. Size is checked first because it is
> cheaper and gives the more useful diagnosis for the common case, truncation. Missing
> metadata **fails closed**; `ALLOW_UNVERIFIED_BACKUP=1` is a loud, logged, documented
> override for the genuine emergency where the sidecar itself is what was lost.
>
> *Write path (beyond the literal scope of item 4, but it is the same finding):* G2's core
> complaint was that nothing ever reads the checksum back, so `nightly-backup.sh` now
> re-hashes the object it just wrote — **before** step 5 deletes the plaintext. A backup
> volume that truncates or corrupts writes is therefore caught while the plaintext still
> exists and can simply be re-encrypted, rather than at the next restore, when the report
> would be "your only backup is corrupt" and nothing could be done about it.
>
> Executed against the real scripts with `pg_basebackup`, `psql` and `gpg` stubbed: **8
> restore scenarios / 28 assertions** and **3 backup scenarios / 16 assertions**, all
> passing. Coverage includes a single byte flipped in the stored object (caught by the SHA
> while the size still matched), a truncated object (caught by size), absent and unparseable
> metadata (both fail closed with the prior restore tree intact), the documented override,
> and a fault injected *between* hashing and read-back (fails, names both digests, plaintext
> retained). One harness expectation was wrong rather than the script: a junk decrypt exits
> **2**, not 1, because `set -o pipefail` propagates `tar`'s own status — correct behaviour,
> and `failure-drill.sh:267` tests it boolean-ly.
>
> **Collateral check that made fail-closed safe:** the only script in the kit that creates a
> base backup is `rebuild.sh:84`, via `nightly-backup.sh`, which always writes the sidecar.
> Nothing fabricates a `.gpg` by hand, so no existing drill can be broken by requiring
> verification. Both callers — `restore-drill.sh:39` (direct) and `failure-drill.sh:267`
> (boolean) — inherit it unchanged.
>
> **Still open:** V43's `backup_verification_age` presumes verification on a *schedule*.
> Nothing performs a periodic restore-verify; that needs the scheduler from item 7.

### G3 — WAL is archived forever and never pruned; the success path can take down production *(high)*

`nightly-backup.sh:82-83` prunes base backups at `BACKUP_RETENTION_DAYS` (default 30).
**Nothing prunes `${BACKUP_STORAGE_PATH}/wal`** — no `pg_archivecleanup`, no `-mtime`
sweep, in any of the ten scripts.

With `archive_timeout=300` (corroborated in `postgres.log` by the 300.1 s checkpoint gap),
that is up to 288 timeout-forced segments a day at 16 MB each — **≈4.6 GB/day** — before
counting segments filled by ordinary write volume. There is no ceiling.

The failure mode is the nasty one: when the archive volume fills, `archive_command` starts
failing; PostgreSQL then **retains WAL in `pg_wal` on the primary**, which fills in turn,
and the primary stops accepting writes. A DR kit whose normal operation can eventually
stop the production database. Retention must be base-backup-aware — keep WAL from the
oldest *retained* base backup forward, and no further.

>
> **✅ CLOSED (item 5, executed).** `nightly-backup.sh` step 4a now records each backup's own
> WAL start segment, parsed from `backup_label` inside `base.tar.gz` *while the plaintext
> still exists* — after step 5 the only copy is a `.gpg` and the backup host holds no private
> key (F-23 FIX 3), so that is the last moment the value can ever be read. Step 7 then removes
> archived segments strictly **before** the oldest *retained* backup's segment and keeps
> everything from it forward, which is exactly the rule this finding asked for.
>
> It is neither an mtime sweep nor `pg_archivecleanup` — the binary is absent here, and it
> could not read the floor out of a sidecar in any case. An mtime sweep is actively wrong:
> a WAL file's mtime is when it was *archived*, after it was written, so keying on a backup's
> own mtime deletes segments that backup needs. The floor comes from the kit's own metadata.
>
> Two properties were tested specifically because both are easy to get wrong. **The floor
> moves with retention:** with an old backup retained, mid-window WAL is kept; expire that
> backup and the floor advances, and the same WAL becomes prunable. **Pruning is safe beside
> a live archiver:** `*.history`, `*.backup` and an in-flight `*.gpg.tmp.<pid>` from a
> concurrent `archive_command` are never candidates, and a segment on a *different timeline*
> is never deleted even when it sorts before the floor — lexical order across timelines is
> not replay order. (The first version of that test proved nothing: a timeline-2 segment
> always sorts *after* a timeline-1 floor, so the guard was never reached. Only a
> timeline-2 floor with timeline-1 segments before it exercises it.)
>
> Fail-safe by construction: with no retained backup, or a sidecar carrying no usable
> `wal_start_segment` (any backup written before this fix), pruning is **skipped** with a
> warning rather than run against a guessed floor. `WAL_PRUNE_DRY_RUN=1` logs the decision
> without deleting; `WAL_RETENTION_ENABLED=0` disables the step.
>
> **Still open:** this bounds the archive only when the job runs. V43's
> `backup_verification_age` needs verification on a *schedule*, and it is item 7 that makes
> both the nightly backup and this pruning actually happen nightly.

### G4 — `${PWD}` is baked into generated PostgreSQL configuration *(medium)*

```
restore-database.sh:79  restore_command = '${PWD}/scripts/wal-restore.sh …'   → postgresql.auto.conf
setup-cluster.sh:56     archive_command = '… ${PWD}/scripts/wal-archive.sh %p %f'  → postgresql.conf
```

Both resolve against the **caller's** working directory, not the script's own. Run either
from anywhere other than the kit root and PostgreSQL is handed a nonexistent path:
recovery fails on a missing `restore_command`, or archiving silently fails and WAL piles up
— which is G3's trigger. The scripts' own usage comments (`bash
gate1-kit/scripts/restore-database.sh "$TARGET_TIME"`, i.e. from the repo root) invite
exactly the invocation that breaks them. `failure-drill.sh:267` gets it right by calling
`bash scripts/restore-database.sh` with cwd already at the kit root, which is why the drill
passed.

*Fix:* `SELF="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` and use `"${SELF}/wal-restore.sh"`.

> **✅ CLOSED (item 6, executed).** Both lines now derive
> `SCRIPTS_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` — the same idiom
> `failure-drill.sh:30` and `rebuild.sh:21` already used for `KIT_DIR`. Verified by rendering
> each generated command and running it through `sh -c` **from `/`**, so any surviving `${PWD}`

> script. G4's fix note is now also stale in one respect — it recommends `"${SELF}/wal-restore.sh"`

### G5 — "Nightly" is not scheduled by anything *(medium)*

There is no cron entry, no systemd unit or timer, and no scheduler wiring for
`nightly-backup.sh` anywhere in the repository — no `*.timer`, `*.service` or `crontab*`
file exists, and nothing in `gate1-kit/` mentions cron or systemd. Tracker B-06 and the
RPO ≤ 300 s story both assume automatic execution. As shipped, a backup happens only when
a human remembers to run the script, so the honest RPO is *"since the last manual run"* —
unbounded. Either ship the unit file or rename the script.

### G6 — Minor, but real

* **No mutual exclusion.** No `flock` in `nightly-backup.sh`. Two runs starting in the same
  UTC second compute the same `BACKUP_FILE` and collide on `tar -czf`; more commonly, a
  slow backup overlaps the next cron tick and doubles the I/O and plaintext window (G1).
* **Retention has no floor guard.** `find … -mtime +30 -delete` applied to both `.gpg` and
  `.meta.json` can delete the **last** restorable backup if the job was broken for over 30
  days. Assert at least one surviving backup before pruning.
* `for f in $(ls -1 "${BACKUP_DIR}"/basebackup_*.gpg | sort)` (`restore-database.sh:35`)
  word-splits on any storage path containing spaces.
* `gpg --recipient-file` requires GPG ≥ 2.2.x — an undeclared prerequisite on the backup host.
* `WAL_POSITION` falls back to `|| echo 'unknown'`, so a failed `psql` silently records
  unusable metadata instead of failing the backup.
* Base backups are **double-gzipped**: `pg_basebackup --compress=gzip:6` already produces
  `base.tar.gz`, which `tar -czf` then recompresses. Pure waste, and it inflates G1's
  plaintext window.

>
> **🟠 PARTIALLY CLOSED (item 5, executed).** Three of these six bullets are fixed, and they
> had to be fixed together because they are coupled: **mutual exclusion** (`flock` on a
> shared `GATE1_LOCK_FILE`, refused rather than queued, and failing **open** with a warning
> if `flock(1)` is absent — "no backup exists" is a worse DR outcome than "backup taken
> without mutual exclusion"), the **retention floor guard** (the newest backup is never
> pruned, and a sidecar is removed only together with the archive it describes), and the
> **word-splitting loop** in `restore-database.sh` (now a `nullglob` array). The lock is
> shared with `restore-database.sh` on purpose: the harm is not I/O contention, it is a
> backup pruning the archive underneath a restore that is replaying from it. `wal-archive.sh`
> and `wal-restore.sh` must never take it — PostgreSQL spawns them *while* it is held.
>
> Bullet 1's same-second collision needed a second guard beyond the lock: `flock` serialises
> runs but does not make `TIMESTAMP` unique, so a run finishing inside the same UTC second
> still computed the same `BACKUP_FILE` and would have overwritten a backup already in the
> archive. It now refuses.
>
> Two further paths touch the locked state, and both were found **only by re-reading** — the
> suite was green and mutation-complete when they were found:
>
> * `rebuild.sh --clean` deletes `${BACKUP_STORAGE_PATH}`, which is **where the lock file
>   lives**. Deleting a lock file does not release it: the holder keeps the inode while the
>   next run locks a brand-new file, so exclusion silently vanishes with both runs
>   proceeding — and the same wipe takes `${RESTORE_PARENT}` with it. The wipe now runs inside
>   a scoped non-blocking `flock` and is refused if one is held. It has to be *released*
>   before the sub-scripts run, because `nightly-backup.sh` and `restore-database.sh` take
>   that same lock and would otherwise be refused by their own parent. Even that was
>   incomplete, and the third re-read caught it: the wipe still **unlinked the lock file while
>   holding it**, which moves the same hole inside the critical section — a later run opens a
>   fresh inode at that path and acquires it immediately. It now deletes the *contents* of the
>   backup tree, sparing the lock file (T23) — matched **by inode** (`-samefile`), because
>   `-path`/`-name` are globs and a `${ROOT}` containing `[ ] * ?` would miss the literal name
>   and delete the lock after all (T24); and guarded on the lock file existing, because
>   `-samefile` on a missing path fails closed and deletes nothing, which is the state the
>   fail-open branch is in (T25).
> * `restore-database.sh` installed its `UNPACK_DIR` EXIT trap **above** the lock, so a
>   *refused* restore deleted the unpack directory belonging to the run that held the lock —
>   the decrypted `base.tar.gz` and `pg_wal.tar.gz` it was mid-extraction on. The refusal path
>   disarms the trap first, because a refused run must be a no-op.
>
> A lock protects the work inside the critical section. It says nothing about cleanup handlers
> installed before it, and nothing about a third script deleting the lock's own file; both had
> to be handled explicitly (T21–T25, mutations 11–15).
>
> **Still open:** the undeclared GPG ≥ 2.2 prerequisite for `--recipient-file`; the
> `WAL_POSITION … || echo 'unknown'` fallback, which records unusable metadata instead of
> failing the backup (the new `wal_start_segment` path *is* validated — a malformed value is
> discarded and logged rather than recorded as if it were a floor — but `wal_position` still

### G8 — The generated PostgreSQL commands could never have run from a fresh clone *(high — found 2026-09-21 while executing item 6)*

G4 identified the wrong *directory* on these two lines. Actually executing them found a
second, independent defect on the same two lines, and it is the worse of the two because it
does not depend on how anyone invokes anything:

```
git ls-files -s gate1-kit/scripts/     → all ten scripts are mode 100644
```

PostgreSQL runs `archive_command` and `restore_command` through `/bin/sh -c`, and both
referenced their script as a **bare path**. A shell cannot execute a file without the
executable bit. Reproduced:

| Form (cwd `/`, 644 copy of the real script) | Result |
| :--- | :--- |
| `sh -c '<abs path>/wal-archive.sh %p %f'` | **exit 126** — `sh: 1: …/wal-archive.sh: Permission denied` |
| `sh -c 'bash "<same 644 file>" %p %f'` | script runs — reaches its own `wal-archive:` logging |
| `sh -c '<abs path>/wal-restore.sh …'` | **exit 126** — same |
| `sh -c 'bash "<same 644 file>" …'` | runs, exits 1 correctly (segment not yet archived) |

So from a clean `git clone`, `setup-cluster.sh` writes an `archive_command` that fails on
**every** WAL segment and `restore-database.sh` writes a `restore_command` that fails on
**every** replay — while PostgreSQL keeps reporting itself healthy. That is defect 7's
failure mode (`README.md:168`) and G3's trigger, reintroduced by a different route: WAL
accumulates unarchived, the RPO guarantee becomes unbounded, and a real restore finds
nothing to replay. Nothing alerts.

Why the drill evidence still looks like success: every *human* and *script* invocation in the
kit goes through `bash scripts/…`, which needs no executable bit (`README.md:70–83`,
`rebuild.sh:73–81`, `failure-drill.sh:267`, `restore-drill.sh:39`). The two commands
PostgreSQL executes are the only two that do not — and they are also the only two whose
failure is silent. The evidence in `gate1-drill/` was therefore produced by a working copy
that *had* the bit set, a state git does not preserve.

*Fix (applied):* invoke through `bash "${SCRIPTS_DIR}/…"` so the executable bit is
irrelevant to recovery, **and** commit the scripts `100755` so direct invocation works too.
Either alone leaves a trap: `bash`-only breaks the moment someone "tidies" the command back
to a bare path, and the mode bit alone is lost by any zip, copy, or checkout onto a
filesystem that does not carry modes — which is most likely how it was lost here. Also
quoted `"${WAL_DIR}"` and `"${BACKUP_GPG_HOME}"` in `restore_command`, which were previously
bare and would break on a path containing a space.

*Verification:* all four rows of the table above re-run against the fixed scripts — the two
generated commands now expand to absolute, cwd-independent paths, reach their scripts, and
no live `${PWD}` remains anywhere in `gate1-kit/scripts/` (the only surviving mentions are
the comments explaining why it must not be used). `bash -n` clean on all ten scripts. No
script or test in the kit asserts on the old command string, so nothing else needed
updating — except `rebuild.sh:14–17`, whose NOTE documented the `${PWD}` behaviour as
intentional and had to be corrected.

* **G8** was invisible in the *same file*, on the *same two lines*, that G4 had already been

  command found the permission failure.

  definitions had been silently emptied — and a whole feature (bed capacity) that never
  reaches the server at all.
* **Item 4** was scoped "S" and the *fix* was indeed small; nearly all the effort was making
  it verifiable. With no PostgreSQL, no `gpg` and no `pg_basebackup` in the sandbox, the only
  honest way to test a DR script is to stub those four tools and inject faults — a flipped
  byte, a truncated object, a missing sidecar, corruption *between* hashing and read-back.
  Item 8 should be estimated on that basis, not on the size of its diff. Where a
  harness and a script disagreed, the harness was wrong twice (an over-specific exit code,
  a marker cleared before the stub could see it) and the script was wrong zero times — worth
  remembering before "fixing" a script to satisfy a test.
* **Item 5** looked like "add a cleanup sweep". It was really "record a new fact at the only
  moment it is observable": the WAL floor has to be parsed out of `backup_label` *before* the
  plaintext is deleted, because afterwards the backup host holds no private key and can never
  read it again. A retention rule whose input is unavailable at retention time is not
  implementable, so the change belongs in the backup path, not the cleanup path. Its `flock`
  is also a reminder that the load-bearing part of a lock is often where it is *absent*:
  `wal-archive.sh` and `wal-restore.sh` must stay unlocked, because PostgreSQL spawns them
  through `archive_command` / `restore_command` while the holder is waiting. And the timeline
  test passed for the wrong reason until it was inverted — a check that cannot fail is not a
  check, which is why every harness here is mutation-tested before its number is quoted.

In each case the estimate was right about the *fix* and wrong about the *finding*. The
remaining effort columns should be read as "time to fix once found", not "time to close".
